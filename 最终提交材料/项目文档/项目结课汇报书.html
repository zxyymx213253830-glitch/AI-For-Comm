01项目功能总览

1.1系统定位

系统接收一句通信领域的自然语言输入，自动完成路由判定、智能体调用与本地工具执行，输出两类结果之一：一段带依据的专业答案，或一份含真实仿真图表、经独立校验的研究报告。

系统提供两种工作模式，共用同一套智能体资产与本地工具层：

模式 输入 内部动作 输出 典型耗时
① 快问快答（单智能体直答） 一个具体问题 关键词打分路由 → 单个专家作答 → 按需回环调用本地工具 结构化答案 + 工具使用标识 35 ~ 250 秒
② 科研任务（六步流水线） 一个研究课题 拆解 → 文献综述 → 多专家并行论证 → 交叉校验 → 闭环修正 → 分段统稿 → 渲染 HTML 研究报告（内嵌真实仿真图） 5 ~ 14 分钟

两种模式共用同一个 AgentNode 对象、同一份 config.json、同一套 tools/ 工具白名单：快问快答是流水线第 3 步的单点形态，流水线是快问快答的多点编排形态。

1.2功能清单

# 功能 入口 触发方式 产出

1.3模式一：快问快答

路由规则。 路由是一张关键词打分表（web/routes/helpers.py），问题文本按命中次数为每个智能体计分，取最高分；全部未命中时落到默认路由 comm_agent：

目标智能体 触发关键词（不区分大小写） 对应职责
math_agent AWGN、SNR、BER、香农、信道容量、互信息、熵、编码、调制、公式、推导、计算 信息论与数学推导
comm_agent GTP、S1AP、NAS、3GPP、协议、信令、组网、RRC、切换、5G、4G、LTE 3GPP 协议与信令
hw_agent Verilog、FPGA、Vivado、硬件、时序、综合、RTL、模块 FPGA / Verilog 实现
sim_agent 仿真、蒙特卡洛、模拟、曲线、误码率仿真 数值仿真验证
lit_review_agent 综述、文献、调研 文献综述（CLI 侧优先判定）

两条入口的路由实现有意不同：Web 走纯打分制，稳定且适合演示；CLI 额外做两件事——命中"综述/文献"时直接调用 LitReviewAgent.survey()；命中数学类或无匹配时调用 orchestrator.dual_verify()，即 math_agent 推导 → verify_agent 审稿 → 不通过则修正重提的双节点闭环（最多 3 轮）。

单答同样带本地工具。 每次提问都经过 ask_with_tools()：驱动器先按问题关键词本地预跑 1~2 个离线工具（标准误码率曲线、香农容量、本地知识库摘录），把真实数值连同工具说明书一并交给智能体；智能体可直接引用这些数值，也可按协议申请更多工具，本地执行后结果回喂，再定稿（协议见 2.5）。前端据此在答案下方显示工具徽标。

1.4模式二：六步科研流水线

步 名称 执行者 输入 输出 失败时的降级动作
1 问题拆解 规划者角色（候选 comm_agent→math_agent） 一句课题 ≤5 个子问题的 JSON，标注归属专家 解析失败→整题交给 comm；候选空回复→换下一候选
2 文献调研 lit_review_agent 课题 + 子问题清单 公网（arXiv/Semantic Scholar）+ 平台知识库双源综述 公网不可用→退化为纯平台库；异常→标注降级并继续
3 并行咨询专家 math / comm / hw / sim 文献综述 + 各自子问题 各专家完整论证 + 自主申请的工具清单 单专家失败只警告不中断；sim 有三级提示词退让
3.5 仿真代码真执行 本地沙箱 sim 答案中的 Python 代码 stdout + PNG 图表（自动回收） 未提取到代码→记录原因，不编造结果
4 交叉校验 verify_agent 综述节选 + 全部专家论证 【通过】/【有条件通过】/【不通过】三级意见 平台异常重试 1 次，仍失败→标注跳过并继续出报告
4.5 闭环修正 原专家 + verify_agent 评级为【不通过】的条目 修正后的论证 + 二次评级（≤2 轮） 轮次耗尽→保留现状并在报告中如实标注
5 分段统稿 report_agent + 本地合并 每位专家的完整论证（每次只送一位） 固定 7 字段 JSON 分节失败→原文直录；全局失败→本地补齐；平台全挂→机械拼装
6 报告渲染 本地渲染引擎 统稿 JSON + 全部原始材料 + 消息轨迹 outputs/research_<时间戳>.html 渲染异常→记录错误，前序产物不丢

两条设计约束：

  • 同一专家至多领一道子问题。规划者若拆出两道同归属的子问题，第二道并入同一次提问作为补充，不并发开两个会话，以规避平台同会话并发锁。
  • 并发度固定为 2。同时打开的网关 SSE 连接数限制在 2，超出会触发网关限流。

1.5报告产出的固定形态

流水线产出的每份报告为单文件 HTML，自带样式与内嵌图片，可离线打开、可整文件转发，章节结构固定：

章节 内容 数据来源
封面 课题、执行摘要、关键词、耗时与参与智能体 report_agent summary / keywords
Ⅰ 协作链路 各环节产出材料的字符量 本地 steps 消息轨迹
Ⅱ 研究背景与文献综述 综述全文，含来源标注与参考文献 lit_review_agent
Ⅲ 核心发现 每位专家一节正文 + 该节仿真图表 + 可展开的专家原文 report_agent 分节统稿 + 专家原文
Ⅳ 交叉分析 各专家结论是否互相印证、理论值与仿真值是否一致 report_agent cross_analysis
Ⅴ 校验意见 三级评级与逐项核对结论，原样转述 verify_agent
Ⅵ 综合结论与展望 结论以评级开头 + 后续可执行验证建议 report_agent conclusion / outlook
附录 协作过程留痕（消息轨迹表 + 材料体量与全文位置） 本地编排层

1.6交付形态

  • Web 应用：Flask，六个中文页面（/ 实时对话、/research 发起研究、/reports 报告库、/reports/view/<file> 在线查看、/monitor 监控、/settings 设置）；页面模板在 web/templates/，样式在 web/static/css/style.css，交互脚本在 web/static/js/（六个页面各一份），设计系统为深海军蓝 + 琥珀金，配自研 logo。
  • 命令行：python main.py，双模式文本交互，适合无人值守与录屏。
  • 容器：Dockerfile + docker-compose.yml，内网演示环境常驻 7860 端口。
  • 报告归档：outputs/ 目录累计研究报告 17 份，仿真图表在 outputs/sim/。

02系统架构与智能体之间的通信

本章回答一个核心问题：七个运行在远端平台上的智能体彼此不能直接通信，系统如何将它们组织为协作整体。

2.1分层架构：大脑在平台，手脚在本地

┌─ 本地应用层 ─────────────────────────────────────────┐
│  Web（Flask · 6 页中文）   CLI main.py   Docker/7860                                           │
│  对话 / 研究 / 报告库 / 监控 / 设置                                                            │
├─ 本地编排层 core/ ──────────────────────────────────────┤
│  ResearchPipeline（六步流水线，星型中枢）                                                      │
│  Orchestrator（路由 route / 双节点 dual_verify）                                               │
│  AgentNode（会话·SSE·空回复重试·知识库挂载）                                                   │
│  MessageBus（内存邮箱）  tool_driver（工具回环）                                               │
│  report.py（HTML 渲染）  config_manager  logger  lit_search                                    │
├─ 本地工具层 tools/  ─────────────────────────────────────┤
│  SymPy 推演/恒等式复核 · 通信算法库 · Python 沙箱执行                                          │
│  Verilog 编译仿真 · 公网文献检索 · 本地资料检索 · 注册表/白名单                                │
├─ HTTP/SSE  ·  平台层 OpenTrek ────────────────────────────────┤
│  7 个智能体（角色对话型 · ReAct 引擎）· 5 个知识库                                             │
│  4 个 API 工具（搭载至对应智能体）· 3 个技能（Skills Hub）                                     │
└────────────────────────────────────────────────┘

分工原则：需要稳定、可审计、真算真跑的能力放本地，需要模型能力、知识检索、版本治理的能力放平台。两侧之间只有一个接口——core/agent_node.py 中约 200 行的 HTTP/SSE 客户端。

2.2拓扑选择：星型

点对点的智能体互调在本平台不可行，原因有三条硬约束：

  1. 角色对话型智能体不能被另一个智能体调用，平台不提供 agent-as-tool 的互挂能力；
  2. 每次调用都是无记忆的，一次 /run 结束即完成使命，无法在其内部等待第三方回复；
  3. 平台没有回调或 webhook 入口，不会主动把消息推给本地。

因此系统采用星型拓扑：编排器（ResearchPipeline + Orchestrator + MessageBus）是全图唯一枢纽，所有智能体只与编排器相连，任意两个智能体之间的"对话"实际上是编排器把一方产出注入另一方的下一次提问。

                 ┌──────────── 编排器（本地） ────────────┐
   plan ────────▶│ comm  math  hw  sim  lit  verify  report│
                 │   ▲     ▲    ▲   ▲    ▲      ▲      ▲   │
                 └───┼─────┼────┼───┼────┼──────┼──────┼───┘
      send/receive   │     │    │   │    │      │      │
      全部经中枢代投递└─────┴────┴───┴────┴──────┴──────┘
                     任何两个智能体之间没有直接边

代价是多一次中枢搬运，收益是协作过程完全可记录、可重放、可降级，报告附录的"协作过程留痕"直接由此生成。

2.3通信通道之一：平台调用协议（纵向，本地 ↔ 平台）

所有智能体共用一套调用协议，由 AgentNode 封装。平台侧接口文档见 docs/平台参考资料/（创建会话、创建连接、发起 agent 调用、发起一次对话、知识库检索共 5 份）。

第一步 建会话

POST {base}/createSession
Body: { "agentCode": "<UUID>", "agentVersion": "<版本编码>" }
Resp: { "data": "<uniqueCode>" }     ← 即 sessionId，一个 AgentNode 一个专属会话

base 为 http:///sfm-agent-studio/sfm-api-gateway/gateway/agent/api，鉴权统一为 Authorization: Bearer <APP_KEY>。

第二步 发起对话（流式）

POST {base}/{agentCode}/run
Body: { "agentVersion": "...", "sessionId": "...", "stream": true, "delta": true,
        "input": "<提示词>", "kbIds": ["..."] }      ← 有 kbIds 时平台自动做知识库检索

第三步 解析 SSE 流。平台以 data:{...} 逐帧推送，本地按对象类型分流：

SSE 对象 含义 本地处理
thought.delta ReAct 思考过程增量 默认丢弃；collect_thought=True 时缓存备用
message.delta 旧版回答增量（累计） 计入终答
text.delta 新版回答增量（累计） 计入终答
complete 流结束 立即退出读取

终答取用采用双保险：若 text.delta/message.delta 拼接结果为空或过短，自动回退到缓存的 thought.delta，避免把过渡语当成答案。

第四步 会话无记忆 → 上下文由本地重建。平台不保留上一轮，因此工具回环、闭环修正等多轮交互，本地都必须把"原始问题 + 上一轮回答 + 工具结果"整段重新拼进新的 input。

超时与硬限制。本地 requestTimeout/sseReadTimeout 均配 300 秒，但平台侧"任务规划套件-结果渲染"环节存在约 180 秒的硬超时，超过即断流并返回不完整响应。为此本地实现两道抢救：_repair_truncated() 对被截断的 JSON 补齐闭合结构后再解析，_fix_escapes() 修复 LaTeX 命令被当作非法转义导致的解析失败。

2.4通信通道之二：内存消息总线（横向，智能体 ↔ 智能体）

智能体之间的传话由 core/message_bus.py 承担，提供 register / post / fetch 三个方法；AgentNode 对外暴露 send() / fetch_messages() 两个动作。消息结构为 { "from", "to", "type", "content", "ts" }，按收件人姓名路由到内存邮箱，取完即清。

在用的消息类型：

type 方向 场景
derivation / feedback math ↔ verify 快问快答的双节点校验
sub_question / answer 编排器 ↔ 专家 流水线第 3 步并行咨询
summary lit → 编排器 文献综述回传
verdict / correction verify ↔ 编排器/专家 评级与闭环修正
angle@<专家> 规划者 → 编排器 拆解出的每个子问题
digest@<专家> / global report → 编排器 分节统稿 / 全局统稿结果

总线是逻辑信箱而非网络组件：纯 Python 进程内 defaultdict(list)，不落盘、不走网络。它解决的是消息语义与投递记录，真正的数据搬运发生在编排器的函数调用里。这一取舍使整条流水线可以在断网环境下用 mock 完成单元测试。

同时 _record() 会把每次投递的 (step, from, to, type, chars) 追加进 pipeline.steps，最终写进报告附录，使通信过程本身成为交付物的一部分。

2.5通信通道之三：工具回环协议（智能体 ↔ 本地工具）

平台智能体无法自行充当 MCP 客户端，因此本项目自定义了一套纯文本协议，使智能体能够驱动本地工具。

请求格式（写在智能体回答里，一行 JSON，用中文方括号包裹）：

〔工具请求〕{"name": "sympy_check_equality", "arguments": {"left": "...", "right": "..."}}〔/工具请求〕

不使用标准代码围栏，原因是平台 SSE 对围栏的截断处理会打断流，中文标记不会被围栏解析器吞掉。

结果回注格式：

〔工具结果 run_python｜执行成功〕{"returncode": 0, "stdout": "..."}〔/工具结果〕

回环控制参数（core/tool_driver.py）：

参数 取值 作用
MAX_TOOL_ROUNDS 2 一个问题最多两轮工具回环
MAX_CALLS_PER_ROUND 3 单轮最多执行 3 个请求
RESULT_MAX_CHARS 2500 单个工具结果注入提示词的上限
MAX_PREFLIGHT 2 每次提问最多预跑 2 个离线工具
上下文重建 原问题 + 预跑结果 + 工具说明书 + 上轮回答（截 4000 字）+ 工具结果 补偿会话无记忆
定稿条件 回答中不再出现工具标记 剥除标记后返回

确定性预跑。工具回环若完全依赖模型自愿申请，实际执行率极低。因此驱动器在发出首轮提问之前，先按"专家权限 + 题干关键词"本地真跑 1~2 个参数可自动推导的离线工具（comm_lib 标准算法库、protocol_lookup 本地知识库），把真实数值以"系统已真实执行"段落压进提示词并要求模型引用而非覆盖。预跑以 round=0 事件留痕，与自愿申请的 round≥1 区分；预跑失败的结果不进提示词，只写日志。run_python / run_verilog 需要模型提供代码，仍走自愿申请通道。

最小权限白名单（tools/registry.py，未列出的智能体退化为普通问答）：

智能体 可用本地工具
math_agent sympy_compute、sympy_check_equality、comm_lib、protocol_lookup、search_papers
sim_agent run_python、comm_lib、sympy_compute、protocol_lookup、search_papers
hw_agent run_verilog、comm_lib、sympy_compute、protocol_lookup、search_papers
comm_agent protocol_lookup、comm_lib、sympy_compute、search_papers
verify_agent 六个工具全开（审稿需要自行复算）
lit_review_agent 无（自身即检索器，内部直调工具）
report_agent 无（只统稿，不产生新事实）

容错解析。模型写坏 JSON 属高频事件，提取器先用 raw_decode 严格解析，失败则退化为正则抠出工具名、参数置空，由注册层回一句中文的参数说明引导下一轮改对。工具执行的任何异常都被翻译成中文结果返回，工具永远有回复，流水线不会因一个坏参数卡死。

03三个核心机制

本章说明三项关键机制：仿真真执行、校验真闭环、统稿保内容。

3.1机制一：仿真真执行闭环

原则：凡可本地计算的，一律本地真算，算完把产物嵌进报告。仿真不是"给一段代码看看"，误码率曲线必须由真实执行产生。

线路 谁产出代码 谁执行 执行器 产物去向
数值仿真 sim_agent 回答中的 Python 代码块 流水线第 3.5 步 _execute_sim_code 本地子进程（tools/sim_tools.execute_python_code，超时 120 秒，强制 MPLBACKEND=Agg） PNG 转 base64 嵌入报告仿真图表区
硬件验证 hw_agent 回答中的 Verilog 本地工具 run_verilog Verilator / iverilog 本机编译执行 编译与仿真结论回注下一轮

实现要点：代码提取与执行逻辑收敛在工具层，与 run_python 共用同一套安全执行实现；执行失败不伪装成功，事件 pipeline.sim.exec_failed 记标准错误输出，报告里该节就没有图；未提取到代码记事件 pipeline.sim.no_code 留痕；硬件仿真选择本地 Verilator 而非外接仿真服务，以满足内网部署下执行链最短、可复现、不引入新依赖的要求。

3.2机制二：三级校验与闭环修正

多专家并行作答必然出现口径不一致、量纲错误、规范版本混用，只校验不修正等于把问题原样交给读者。

  1. 三级评级：verify_agent 的校验提示词硬规定只能给【通过】/【有条件通过】/【不通过】三档，并逐条写理由（量纲检查、单调性、特殊值、文献对照等）；
  2. 闭环修正：评级为【不通过】时，流水线把校验意见拆成反馈发回对应专家重答并重新校验，最多 MAX_CORRECTION_ROUNDS = 2 轮（_verify_with_correction），事件 pipeline.correction.reverify 留痕；
  3. 校验者自己也有工具：verify_agent 白名单含恒等式复核、Python 执行、通信算法库等六个工具，可自行复算；
  4. 评级进报告：全局统稿提示词硬规定 conclusion 字段必须以三级评级开头并忠实转述理由，封面徽章颜色随评级变化。

3.3机制三：分段统稿与高审美渲染

问题：平台单次调用有约 180 秒硬超时，而七智能体的原始材料动辄上万字。把全部材料塞进一次统稿调用并压缩配额，会使专家论证在报告正文中所剩无几。

方案：分段统稿，把一次大调用拆成"每位专家 1 次分节统稿 + 1 次全局统稿"：

子任务 输入 输出 配额
分节统稿 ×N 单专家完整论证（上限 6000 字）+ 其子问题 findings 仅 1 条 正文 600~800 字，保留全部关键公式、数值与规范编号
全局统稿 ×1 文献综述截 1800 字 + 每专家摘要 260 字 + 校验截 900 字 摘要/背景/交叉/结论/展望/关键词 按角色手册满额 300/400/400/300/200 字

单次调用的输入输出都变小，从而避开硬超时；分节统稿用 2 线程并发（ThreadPoolExecutor）控制总时长，且每次调用开独立会话以规避平台同会话并发锁。

三层兜底：单节统稿失败 → _digest_fallback 原文直录（上限 2500 字，标记 degraded）；全局统稿失败 → 本地补齐全局字段，分节内容不受影响；平台全挂 → _fallback_draft 本地机械拼装七字段。另有三道解析保险：_repair_truncated（截断 JSON 补闭合）、_fix_escapes（非法转义双写）、restore_latex_ctrl（还原被 JSON 吃掉的反斜杠，公式不露源码）。

渲染层：报告为单文件 HTML，靛蓝瓷主题（深蓝封面 + 金色章号 + 衬线标题）、KaTeX 公式、代码高亮、仿真图内嵌、每节末尾"专家原文全貌"可展开折叠区、附录协作过程留痕表。排版库依赖外网时存在退化风险，故内置本地 Markdown 渲染器（覆盖标题、表格、引用、列表、代码围栏、粗斜体），外网库不可达时自动接管。

3.4六道质量门

三个机制在一次科研任务中的咬合顺序：拆解 → 文献 → 专家作答（工具预跑 + 工具回环）→ 仿真真执行 → 三级校验与闭环修正 → 分段统稿与渲染。在此之上设置六道质量门：

质量门 实现
① 拆解覆盖门 拆解结果必须 ≥3 题且 ≥3 类专家；不合格带补正指令重问一次；仍不合格按缺失视角本地回填模板子问题
② 工具优先门 工具说明书压在"一次性输出"后缀之后，并附工具优先指令：先申请工具、后给终答
③ 独立会话门 每次 think() 开独立会话，会话 ID 局部化，支持多线程并发调用同一智能体
④ 本地排版门 内置本地 Markdown 渲染器兜底，外网库不可达时正文不退化为裸文本
⑤ 工具预跑门 驱动器按权限与关键词先本地真跑离线工具，把真实数值压进首轮提示词；两个离线工具权限扩至全体专家
⑥ 公式卫生门 解析后按命令白名单还原被吃反斜杠；\text{} 内下划线转为 KaTeX 可接受写法；渲染前 sanitize_math 统一收口

门②依赖提示词、门⑤不依赖模型自觉，二者构成同一通道上的两层。六道门均有离线回归覆盖，见 6.4。

4.2math_agent：信息论与数学推导

  • 能干什么：信道容量、误码率、频谱效率等公式推导与量级估算；恒等式与不等式证明；分贝与线性、带宽与速率的数值换算；推导结果自查与修正。
  • 手册硬规则：推导规范与"推导三步法自查"、数值计算注意事项、发送 verify 前的自检清单、约束节。
  • 工具用法：sympy_compute 做符号化简与求导，sympy_check_equality 复核恒等式，使每步可复算；comm_lib 提供标准误码率与容量数值作为量级参照，protocol_lookup 提供本地知识库公式摘录，两者由驱动器预跑。
  • 本地便捷方法：solve_awgn_capacity(带宽, 信噪比)、derive_capacity_change(场景)。
  • 边界：超长推导可能触及平台 180 秒硬超时，由截断抢救与重试处置。

4.3comm_agent：3GPP 协议与组网（兼默认规划者）

  • 能干什么：规范条款查询（编号、版本、章节）、信令流程分析、组网与参数配置解读、协议演进对比；兼任流水线第 1 步的问题拆解（PLANNER_CANDIDATES 首位）。
  • 手册硬规则：回答必须给规范编号与版本；不确定时明说"需查规范"，不编造。
  • 工具用法：protocol_lookup 查本地协议知识库条目（驱动器预跑一次，命中摘录直接摆在它面前）；comm_lib 取标准算法库数值；sympy_compute 核算功率与链路预算公式。
  • 本地便捷方法：query_protocol(问题)。
  • 边界：规划输出受拆解覆盖门约束（≥3 题且 ≥3 类专家）；离线时规划回退 math_agent，再不行由本地回填模板子问题。

4.4hw_agent：FPGA / Verilog 硬件实践

  • 能干什么：按规格生成可综合 Verilog 模块（译码器、滤波器、接口等）；时序与关键路径分析；查找表、寄存器、块存等资源开销估算；测试激励编写。
  • 手册硬规则：输出格式节（平台渲染要求）、代码规范、禁止节，以及验证闭环必做——生成后必须经 run_verilog 本地编译或仿真，不允许只给代码不给结论。
  • 工具用法：run_verilog 调本机 Verilator / iverilog，编译与仿真结论回注下一轮；comm_lib、sympy_compute、protocol_lookup 提供可预跑的数值与规范依据。
  • 本地便捷方法：generate_verilog(规格)、explain_timing(模块代码)。
  • 边界：平台上存在多版本并存，以 config.json 中版本为准；RTL 仿真依赖本机已装工具链，换机部署需先安装。

4.5sim_agent：蒙特卡洛仿真与数值验证

  • 能干什么：误码率、容量、星座图、收敛性等仿真方案设计与代码生成；理论曲线对照与偏差分析；仿真五步法执行（方案 → 代码 → 运行 → 对照 → 结论）。
  • 手册硬规则：仿真五步法必做；禁止编造运行结果；输出格式固定四章节。
  • 工具用法：run_python 本地真跑、comm_lib 调通信算法库、sympy_compute 算理论值、protocol_lookup 查本地知识库；comm_lib 会被预跑一次，仿真开始前即取得理论基准曲线。
  • 本地便捷方法：simulate_ber(调制方式,…)、simulate_capacity(信噪比范围)、think_verified(任务)（生成 → 执行 → 偏差校验 → 不达标自动反馈重跑）、execute_code(代码)。
  • 边界：复合提示词易导致规划超时，流水线对其改用精简提示词（只给课题与子问题，不注入全文综述），并由个性化交付指令要求四章节一次性输出。

4.6lit_review_agent：公网 + 知识库双源文献调研

  • 能干什么：arXiv / Semantic Scholar 公网检索与平台知识库检索双源融合；按子问题角度组织综述；生成带作者年份或规范编号标注的参考文献清单。
  • 手册硬规则：综述流程三步规范；结论必须有出处标注；无出处的论断标"待验证"。
  • 工具用法：不挂白名单，内部直调检索工具（core/lit_search），避免回环套回环。
  • 本地便捷方法：survey(课题)、survey_with_angles(课题, 角度列表)、_attach_web_refs（公网参考文献注入）。
  • 边界：公网不可达时自动退化为仅知识库源，综述标注来源受限；检索源限流时进入冷却并切换可用源。

4.7verify_agent：三级校验

  • 能干什么：对 math / comm / hw 产出做原理性审查——量纲检查、单调性、特殊值、文献对照、规范版本核对、代码可综合性判断；给出三级评级与逐条理由。
  • 手册硬规则：通用四项清单 + 三类专项检查；回复格式硬规定三档评级模板；禁止"看起来没问题"式空话。
  • 工具用法：六个工具全开，可自行复算恒等式、重跑仿真片段、调标准算法库取基准值；校验前驱动器按课题预跑一次，使其先握有真实数值再读专家结论。
  • 本地便捷方法：check_derivation(内容, 主题)。
  • 边界：校验输入为综述截 1000 字 + 每专家截 1500 字（约 4200 字），超长课题会损失细节。

4.8report_agent：统稿主编

  • 能干什么：把多智能体产出统稿为固定七字段 JSON（摘要、背景、核心发现、交叉分析、结论、展望、关键词）；支持分节统稿与全局统稿两种子任务；遵循编辑方针六条（结论先行、忠实原文、保留评级、交叉印证、缺口诚实、公式规范）。
  • 手册硬规则：输出必须是单个合法 JSON、不含 JSON 以外文字；conclusion 必须以三级评级开头；禁止编造材料中没有的数据。
  • 工具用法：不挂工具，统稿不产生新事实。
  • 本地便捷方法：compile_report(标题, 材料)。
  • 备用手册：report_presentation_system.md（组会与答辩文本模式，四步汇报流程），与在线的 JSON 统稿协议不混用。
  • 边界：平台侧存在 180 秒硬超时与同会话并发锁两类间歇限制，分别由分段统稿与独立会话门处置，另有三层兜底保证报告必出。

4.9分工边界：谁向谁要什么

求助方 被求方 要什么 通道
编排器 comm / math 课题拆解 平台调用
编排器 四专家 子问题论证 平台调用 + 工具回环
编排器 verify 三级校验 平台调用 + 工具回环
编排器 report 分节与全局统稿 平台调用
math / comm / hw verify 反馈修正 编排器代投递（总线）
